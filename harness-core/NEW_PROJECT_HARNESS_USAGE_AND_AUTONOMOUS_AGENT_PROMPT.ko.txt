HARNESS Core 새 프로젝트 적용 구조 및 자율 에이전트 명령문
============================================================

목적
----
이 파일은 HARNESS Core 자산을 새 프로젝트에서 제대로 사용하기 위한 운영 구조와,
완전 자율형 에이전트에게 전달할 수 있는 작업 지시문 템플릿을 기록한다.

HARNESS Core는 단순 프롬프트 묶음이 아니라, 자율형 코딩 에이전트가 evidence,
gate, claim boundary를 따라 안전하게 작업하도록 만드는 하네스 엔지니어링 코어다.


0. 사용 모델 선택
----------------

새 프로젝트에서 HARNESS Core를 쓰는 방식은 두 가지다.

모델 A: HARNESS Core root workspace mode

- `harness-core/` 디렉터리 자체를 새 프로젝트의 작업 루트로 사용한다.
- 실제 제품 코드는 `apps/` 아래에 둔다.
- 제품 스펙, feature 상태, evidence, checker를 HARNESS Core 루트 안에 함께 둔다.
- 완전 자율형 제품 기능 구현에는 이 모델을 우선 사용한다.

모델 B: external project + vendored harness mode

- 기존 프로젝트 루트가 따로 있고, HARNESS Core를 `.harness/harness-core/` 아래에 둔다.
- 새 프로젝트의 product code와 evidence는 기존 프로젝트 루트에 둔다.
- HARNESS Core는 운영 가이드, checker reference, claim boundary reference로 사용한다.
- 기존 제품 저장소에 하네스를 붙일 때 사용한다.

원칙:

1. 새 제품을 HARNESS Core로 처음부터 운영하려면 모델 A를 쓴다.
2. 이미 존재하는 제품 저장소에 HARNESS Core를 붙이려면 모델 B를 쓴다.
3. 어떤 모델이든 HARNESS Core evidence를 제품 claim evidence처럼 자동 승격하지 않는다.
4. `provider-verified`, `adapter-checked`, `production-ready`, `stable`, `release-gated`는 프로젝트별 gate와 evidence가 없으면 계속 blocked다.


1. 킥오프 패킷 구성
------------------

새 에이전트나 다른 머신에 전달할 때는 아래 네 가지 파일로 킥오프 패킷을 만들 수 있다.

1. `HARNESS_CORE_NEW_PROJECT_STRUCTURE.ko.md`
   - 새 프로젝트 구조 가이드

2. `HARNESS_CORE_AUTONOMOUS_AGENT_COMMAND.ko.md`
   - 완전 자율형 에이전트 작업 지시문 템플릿

3. `HARNESS_CORE_NEW_PROJECT_KICKOFF_PACKET.ko.md`
   - 위 두 문서를 합친 단일 킥오프 패킷

4. `HARNESS_CORE_NEW_PROJECT_KICKOFF_CHECKSUMS.json`
   - 전달 파일의 SHA-256 기록

zip으로 묶을 때는 위 문서와 checksum 파일을 포함하되, zip 자체의 SHA-256은 zip 밖의 delivery metadata에 기록한다. archive 내부에 자기 자신의 checksum을 고정하지 않는다.


2. 모델 A: HARNESS Core를 새 프로젝트 루트로 쓰는 구조
-----------------------------------------------------

권장 구조:

```text
harness-core/
  START_HERE_FOR_AGENTS.ko.md
  CURRENT_STATE.json
  CURRENT_STATE.yaml
  AGENT_BOOTSTRAP.ko.md
  AGENTS.md
  README.md

  apps/
    <app-name>/
      README.md
      package.json 또는 pyproject.toml
      src/
      tests/
      public/
      docs/

  product/
    <app-name>/
      PRODUCT_SPEC.ko.md
      PRODUCT_STATE.yaml
      features/
        <feature-id>.yaml

  evidence/
    product/
      <app-name>/
        <feature-id>/
          implementation_report.json
          test_report.json
          gate_report.json
          unresolved_items.json

  release/
    product_<app-name>_<feature-id>_scope.yaml
    product_<app-name>_<feature-id>_claim_boundary.yaml

  tools/
    product/
      check_<app-name>_<feature-id>.mjs

  evals/
    suites/
      product_<app-name>_<feature-id>.yaml
    reports/
      product_<app-name>_<feature-id>_report.json
      product_<app-name>_<feature-id>_report.md

  docs/
    product/
      <app-name>/
        usage.ko.md
        architecture.ko.md
        <feature-id>.ko.md
```

디렉터리 역할:

| 경로 | 역할 |
|---|---|
| `apps/<app-name>/` | 실제 소프트웨어 코드 |
| `product/<app-name>/` | 제품 스펙, 기능 정의, 상태 |
| `evidence/product/<app-name>/` | 구현/테스트/게이트 증거 |
| `tools/product/` | 제품 기능 전용 checker |
| `release/product_*` | 기능별 scope, claim boundary |
| `docs/product/<app-name>/` | 사용자/개발자 설명 문서 |
| `evidence/current-state/` | HARNESS Core 현재 상태 증거 |
| `release/claim_ladder.md` | 허용/금지 claim 기준 |
| `tools/check_*` | 하네스 검증 도구 |


3. 모델 B: 기존 프로젝트에 HARNESS Core를 붙이는 구조
-----------------------------------------------------

권장 구조:

```text
<new-project-root>/
  AGENTS.md
  README.md
  PROJECT_BRIEF.md
  CURRENT_STATE.yaml
  src/
  tests/
  docs/
    architecture/
    decisions/
    handoff/
  evidence/
    current-state/
    runs/
    gates/
    checks/
  release/
    scope.yaml
    claim_boundary.yaml
    blocker_register.yaml
    approval_requests/
  tools/
    check_project_current_state.mjs
    check_project_claims.mjs
    check_project_precommit.mjs
  .harness/
    harness-core/
      AGENTS.md
      START_HERE_FOR_AGENTS.ko.md
      AGENT_BOOTSTRAP.ko.md
      README.md
      CURRENT_STATE.yaml
      profiles/
      tools/
      evidence/reference-baseline/
```

모델 B 원칙:

1. 새 프로젝트의 작업 루트는 `<new-project-root>`다.
2. HARNESS Core는 `<new-project-root>/.harness/harness-core/` 아래에 둔다.
3. 새 프로젝트의 evidence와 HARNESS Core의 evidence를 섞지 않는다.
4. 새 프로젝트의 `CURRENT_STATE.yaml`은 프로젝트 상태를 기록한다.
5. HARNESS Core의 `CURRENT_STATE.yaml`은 HARNESS Core 자체 상태를 기록한다.
6. HARNESS Core 자산을 수정해야 할 때는 `harness adaptation` 작업으로 분리한다.


4. HARNESS Core 배치 방법
-------------------------

agent-ready clean export 사용:

```bash
mkdir -p .harness
unzip /path/to/harness-core-agent-ready.zip -d .harness/harness-core
cd .harness/harness-core
node tools/check_agent_ready_self_contained.mjs
node tools/check_reference_baseline_integrity.mjs
```

canonical export:

```text
exports/harness-core-agent-ready.zip
```

정확한 SHA-256은 archive 외부 delivery metadata 또는 HARNESS Core evidence report에서 확인한다.


5. 새 에이전트 시작 순서
-----------------------

모델 A에서는 `harness-core/` 루트에서 시작한다.

먼저 실행:

```bash
node tools/check_agent_ready_self_contained.mjs
```

그 다음 아래 파일을 순서대로 읽는다.

```text
START_HERE_FOR_AGENTS.ko.md
CURRENT_STATE.json
AGENT_BOOTSTRAP.ko.md
AGENTS.md
profiles/agents/codex_goal_executor.yaml
```

작업 후 기본 HARNESS 검증:

```bash
node tools/check_agent_ready_self_contained.mjs
node tools/check_current_state_alignment.mjs
node tools/check_reference_baseline_integrity.mjs
node tools/scan_prohibited_claims.mjs
git diff --check
```

필요할 때만 추가 실행:

```bash
node tools/validate_alpha.mjs
```

모델 B에서는 프로젝트 루트에서 시작하고, HARNESS Core 자체 health check가 필요할 때만 아래를 별도 실행한다.

```bash
cd .harness/harness-core
node tools/check_agent_ready_self_contained.mjs
node tools/check_reference_baseline_integrity.mjs
```


6. 보호 경로와 금지 작업
-----------------------

제품 기능 구현 중 아래는 수정하지 않는다.

```text
dist/**
node_modules/**
evidence/reference-baseline/**
```

금지 작업:

```text
OpenAI model API call
OpenAI provider rerun
외부 유료 API call, 사용자 승인 없는 경우
local model generation, 사용자 승인 없는 경우
telemetry sink write
npm install
npm ci
new model pull/download
raw request 저장
raw response 저장
secret/API key/auth header 저장
production deployment
release gate rerun
destructive command, 사용자 승인 없는 경우
```


7. 계속 금지되는 강한 claim
--------------------------

새 제품 기능 구현이 성공해도 아래 claim은 자동으로 열지 않는다.

```text
provider-verified
adapter-checked
production-ready
stable
release-gated
bare release-gated
```

제품 기능 구현에서 허용되는 것은 기능 단위의 약한 claim이다.

예:

```text
product-<app-name>-<feature-id>-implemented
product-<app-name>-<feature-id>-tested
product-<app-name>-<feature-id>-gate-passed
```


8. 기능 구현 플로우
------------------

권장 플로우:

```text
1. 현재 하네스 상태 확인
2. product spec 작성
3. feature yaml 작성
4. 앱 코드 구현
5. 테스트 작성
6. 제품 checker 작성
7. evidence report 생성
8. HARNESS 검증 실행
9. 제품 검증 실행
10. 최종 보고
```


9. 기능 스펙 예시
----------------

`product/<app-name>/features/<feature-id>.yaml` 예시:

```yaml
feature_id: feature-001-kanban-board
app: task-board
status: requested

goal:
  summary: 로컬 저장 기반 Kanban 보드 구현
  user_value: 사용자가 브라우저에서 보드/컬럼/카드를 관리할 수 있다.

requirements:
  functional:
    - 보드를 생성할 수 있다.
    - 컬럼을 생성/수정/삭제할 수 있다.
    - 카드를 생성/수정/삭제할 수 있다.
    - 카드를 컬럼 간 이동할 수 있다.
    - 브라우저 새로고침 후에도 localStorage에 상태가 남는다.
  non_functional:
    - 외부 서버가 필요 없다.
    - secret을 사용하지 않는다.
    - 기본 빌드가 통과해야 한다.

acceptance_criteria:
  - 핵심 로직 테스트 통과
  - 빌드 통과
  - README에 실행법 포함
  - evidence report 생성
  - product checker 통과

out_of_scope:
  - 사용자 로그인
  - 서버 DB
  - 실시간 협업
  - 외부 API 연동

allowed_paths:
  - apps/task-board/**
  - product/task-board/**
  - evidence/product/task-board/**
  - docs/product/task-board/**
  - tools/product/**
  - release/product_task_board_*

forbidden_paths:
  - dist/**
  - node_modules/**
  - evidence/reference-baseline/**
```


10. 제품 checker 기본 구조
-------------------------

`tools/product/check_<app-name>_<feature-id>.mjs`는 최소한 아래를 확인한다.

```text
필수 파일 존재
테스트 report 존재
implementation report 존재
gate report 존재
unresolved_items count 확인
보호 경로 수정 없음
강한 claim 미허용
secret/raw payload 저장 없음
```

출력 예시:

```json
{
  "status": "pass",
  "feature_id": "feature-001-kanban-board",
  "implementation_report_exists": true,
  "test_report_exists": true,
  "gate_report_exists": true,
  "unresolved_items_count": 0,
  "protected_paths_modified": false,
  "strong_claims_opened": false,
  "secret_or_raw_payload_stored": false
}
```


11. 새 프로젝트 AGENTS.md 최소 골격
----------------------------------

새 프로젝트 루트의 `AGENTS.md`에는 최소한 아래 항목을 둔다.

1. 프로젝트 목표
2. 현재 작업 루트
3. HARNESS Core 위치
4. product code 수정 가능 범위
5. harness asset 수정 가능 범위
6. 금지 작업
7. 검증 명령
8. claim boundary
9. 커밋/배포 승인 정책

예시:

```markdown
# Project Agent Constitution

This project uses HARNESS Core as the evidence-gated autonomous engineering harness.

Harness location:
- .harness/harness-core/

Before broad or release-sensitive work, read:
- .harness/harness-core/AGENTS.md
- .harness/harness-core/START_HERE_FOR_AGENTS.ko.md
- .harness/harness-core/AGENT_BOOTSTRAP.ko.md
- .harness/harness-core/README.md

Project state lives in:
- CURRENT_STATE.yaml
- evidence/current-state/
- release/claim_boundary.yaml
- release/blocker_register.yaml

Do not claim production-ready, stable, release-gated, provider-verified, or adapter-checked
unless this project has an explicit project-specific gate and evidence bundle for that claim.
```


12. 새 프로젝트 CURRENT_STATE.yaml 최소 필드
------------------------------------------

```yaml
project:
  name: <PROJECT_NAME>
  slug: <project-slug>
  harness:
    name: HARNESS Core
    path: .harness/harness-core
    mode: external_project_usage

stage: project-bootstrap

goal:
  summary: <ONE_SENTENCE_GOAL>
  solved_condition:
    - <observable condition 1>
    - <observable condition 2>

operation_mode:
  primary: project_root
  harness_reference: .harness/harness-core

claims:
  allowed_weak_claims:
    - project-bootstrap-recorded
    - project-current-state-recorded
  blocked_strong_claims:
    - provider-verified
    - adapter-checked
    - production-ready
    - stable
    - release-gated

evidence:
  current_state_dir: evidence/current-state
  gate_dir: evidence/gates

verification:
  required_commands:
    - node tools/check_project_current_state.mjs
    - node tools/check_project_claims.mjs
    - git diff --check
```

15. dependency 추가가 필요한 경우
--------------------------------

에이전트가 새 dependency가 필요하다고 판단하면 자동 설치하지 않고 아래 형식으로 보고해야 한다.

```text
dependency approval required

필요한 dependency:
- <package-name>

필요한 이유:
- <reason>

수정 예정 파일:
- package.json
- package-lock.json, 승인 시

승인 문구:
I approve dependency changes for <app-name> using npm install <package-name>.
```

사용자가 승인하기 전까지 아래는 금지다.

```text
npm install
npm ci
node_modules 수정
```

17. 운영 체크리스트
------------------

새 프로젝트 시작 시:

1. 사용할 모델을 고른다. 모델 A는 `harness-core/` root, 모델 B는 `.harness/harness-core/` reference다.
2. HARNESS Core self-contained check를 실행한다.
3. 프로젝트 또는 제품 `AGENTS.md`를 확인/생성한다.
4. product spec 또는 `PROJECT_BRIEF.md`를 생성한다.
5. `CURRENT_STATE.yaml` 또는 `PRODUCT_STATE.yaml`을 생성한다.
6. `release/*claim_boundary*`를 생성한다.
7. 기능별 evidence 디렉터리를 만든다.
8. product-local checker를 만든다.
9. 첫 검증 결과를 evidence에 기록한다.
10. 강한 claim은 모두 blocked로 유지한다.

작업 종료 시:

1. 변경 범위를 요약한다.
2. 실행한 검증 명령과 결과를 기록한다.
3. unresolved item을 명시한다.
4. claim boundary를 업데이트한다.
5. 보호 경로 수정 여부를 확인한다.
6. secret/raw payload 저장 여부를 확인한다.
7. 커밋이 필요하면 승인 요청 상태로 멈춘다.
