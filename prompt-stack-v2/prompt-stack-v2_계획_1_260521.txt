질문: 내가 하네스 엔지니어링을 적용한 프롬프트 자산을 만들고 있는데, 이건 로컬 LLM에서 유효한 작업이야? 아니면 API 모델에서도 유효한 작업이야?
---
답변:
결론부터 말하면, **둘 다 유효한 작업**입니다. 다만 “프롬프트 자산”을 **순수 프롬프트 텍스트**로 보느냐, 아니면 **모델을 둘러싼 실행·검증·도구·컨텍스트 설계까지 포함한 하네스 자산**으로 보느냐에 따라 적용 범위가 달라집니다.

하네스 엔지니어링은 보통 모델 자체가 아니라, 모델 주변의 **프롬프트, 도구, 컨텍스트 정책, 샌드박스, 훅, 검증 루프, 관찰성, 복구 경로** 같은 실행 구조를 설계하는 작업으로 이해됩니다. 최근 글들에서도 “Agent = Model + Harness”라는 식으로, 하네스를 모델 외부의 코드·설정·실행 로직 전체로 설명합니다. ([Addy Osmani][1])

따라서 네가 만들고 있는 프롬프트 자산은 **로컬 LLM 전용 작업이 아니라 API 모델에도 유효한 작업**입니다.

다만 이렇게 나누는 게 좋습니다.

| 구분                       | 로컬 LLM에서의 유효성                                            | API 모델에서의 유효성                                                                                                                               |
| ------------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 시스템 프롬프트 / 역할 / 금지사항     | 매우 유효. chat template, tokenizer, quantization 영향까지 조정 가능 | 매우 유효. API의 system/developer/user 메시지 구조에 맞춰 적용                                                                                             |
| 출력 형식 / JSON 스키마 / 답변 규격 | 유효하지만 모델별 안정성 차이가 큼                                      | 유효. 특히 structured output, function calling과 결합 가능                                                                                           |
| 툴 사용 규칙 / 함수 호출 규칙       | 직접 파서, 툴 라우터, 실행 루프를 구현해야 함                              | API의 function/tool calling과 결합 가능. OpenAI 문서는 function calling을 모델이 외부 시스템·데이터와 인터페이스하게 하는 방식으로 설명합니다. ([OpenAI Developers][2])             |
| 평가셋 / 실패 사례 / 회귀 테스트     | 매우 유효. 로컬 모델 비교와 튜닝에 좋음                                  | 매우 유효. OpenAI 플랫폼도 prompt와 model output을 평가하는 eval/dataset 흐름을 제공합니다. ([OpenAI Developers][3])                                              |
| 가드레일 / 승인 루프             | 직접 구현 가능                                                 | API/Agent SDK 레벨에서도 구현 가능. OpenAI 문서는 guardrail을 입력·출력·툴 동작 검증에 쓰고, human review로 민감한 액션을 멈추거나 승인하게 할 수 있다고 설명합니다. ([OpenAI Developers][4]) |
| 모델 교체 가능성                | 높음. 단, 모델별 어댑터 필요                                        | 높음. 단, provider별 메시지/툴/정책 차이 반영 필요                                                                                                          |

핵심은 **프롬프트 자산을 “모델별 프롬프트”가 아니라 “모델 독립적인 하네스 명세 + 모델별 어댑터”로 설계하는 것**입니다.

예를 들면 이렇게 나누면 좋습니다.

```text
1. Core Harness Spec
- 목표
- 역할
- 금지/허용 행동
- 출력 형식
- 컨텍스트 사용 규칙
- 도구 사용 규칙
- 실패 시 복구 규칙
- 평가 기준
- 예시 입력/출력
- known failure cases

2. Local LLM Adapter
- llama.cpp / vLLM / Ollama용 chat template
- stop token
- sampling config
- JSON 파싱 보정
- tool-call 텍스트 포맷
- 로컬 RAG/파일 접근 정책

3. API Model Adapter
- system / developer / user 메시지 분리
- function calling schema
- structured output schema
- safety / guardrail 연결
- retry / timeout / rate-limit 정책
- eval 로그와 trace 수집
```

로컬 LLM에서는 하네스 엔지니어링이 특히 강력합니다. 모델의 약점을 프롬프트, chat template, 샘플링, RAG, 후처리, 검증 스크립트로 보완할 수 있고, 같은 하네스로 여러 오픈 모델을 비교할 수 있습니다. EleutherAI의 `lm-evaluation-harness`도 로컬 모델, 상용 API, 커스텀 프롬프트, 커스텀 평가 지표를 지원하는 평가 프레임워크로 소개됩니다. ([GitHub][5])

API 모델에서도 똑같이 유효합니다. 오히려 제품화 관점에서는 API 모델 쪽에서 더 실용적인 경우가 많습니다. API 모델은 기본 성능이 높고, tool/function calling, structured output, eval, guardrail, tracing 같은 기능과 결합하기 쉽기 때문입니다. OpenAI 문서도 API에서 프롬프트를 통해 텍스트, 코드, JSON 등 다양한 출력을 생성할 수 있고, prompt engineering으로 결과를 개선할 수 있다고 설명합니다. ([OpenAI Developers][6])

다만 **완전히 동일한 프롬프트를 로컬과 API에 1:1로 쓰면 안 됩니다.** 모델마다 다음이 다릅니다.

* 지시사항 우선순위 해석
* system prompt 반응성
* tool call 포맷
* JSON 준수 능력
* 긴 컨텍스트 처리 방식
* safety policy
* temperature/top_p 민감도
* 한국어 지시 이해력
* few-shot 예시의 영향

그래서 네 작업을 가장 정확히 표현하면:

> “하네스 엔지니어링을 적용한 프롬프트 자산은 로컬 LLM과 API 모델 모두에 유효하다. 단, 자산의 핵심은 공통 명세로 유지하고, 실행부는 모델/프로바이더별 어댑터로 분리해야 한다.”

내가 추천하는 구조는 이겁니다.

```text
/prompt-assets
  /spec
    task.md
    behavior_policy.md
    output_contract.json
    tool_policy.md
    failure_modes.md
    eval_rubric.md

  /adapters
    /openai
      system.txt
      developer.txt
      tools.schema.json
      response_format.json

    /anthropic
      system.txt
      tools.schema.json

    /local-llama
      chat_template.txt
      tool_call_format.md
      stop_tokens.txt
      sampling.yaml

  /evals
    golden_cases.jsonl
    adversarial_cases.jsonl
    regression_cases.jsonl
    judge_prompt.md
```

정리하면, 네가 만드는 건 단순한 “프롬프트 모음”이 아니라 **모델 운용 자산**에 가깝습니다. 그래서 로컬 LLM에서도 유효하고, API 모델에서도 유효합니다. 차이는 “유효하냐/아니냐”가 아니라 **어느 레이어까지 자산화하느냐**입니다.

가장 좋은 방향은:

**Core는 모델 독립적으로 만들고, Adapter는 로컬/API별로 만든다.**
