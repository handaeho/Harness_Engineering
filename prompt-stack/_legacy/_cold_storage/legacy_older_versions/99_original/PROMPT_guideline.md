# PROMPT_guideline

## 0. Identity

- **Document Name**: `PROMPT_guideline`
- **Role**: Governance and operating constitution layer
- **Primary Function**: Define the official stack, ownership boundaries, shared runtime model, constitutional invariants, activation doctrine, cross-consistency rules, compression integrity, traceability, and release-grade quality doctrine for the prompt system.
- **System Position**: This is the **governance hub** of the stack.
- **Design Objective**:
  - centralize governance
  - distribute execution
  - preserve ownership clarity
  - preserve semantic alignment across variants
  - strengthen chapter-to-stack traceability
  - sharpen Appendix A boundary canon without turning governance into a policy dump
  - preserve bounded control without uncontrolled prompt expansion
  - preserve compression integrity for lightweight and standalone variants
  - improve release-grade auditability for future prompt revisions
- **Non-Function**:
  - This document does not directly answer user tasks.
  - This document does not store immutable example bodies.
  - This document does not replace execution-facing prompts.
  - This document does not re-implement overlay-specific deep policy unless boundary-level reference is required.
  - This document is not a duplication sink for every useful idea in the stack.

---

## 1. Constitutional Principle

The stack is governed by the following principle:

> **Completeness is achieved by ownership clarity, semantic alignment, bounded execution depth, and controlled composition — not by policy duplication.**

This means:

- every load-bearing pattern must exist somewhere in the stack
- not every document should contain every pattern
- each document must own a narrow, explicit responsibility
- cross-document consistency must be achieved by aligned semantics, not repeated prose
- compressed variants must preserve meaning even when they reduce wording
- execution depth must remain proportional to actual task need and budget
- richer pattern coverage must increase usefulness more than it increases token cost

### 3.3 Examples are bounded structure adapters

Examples improve:

Examples do not replace:
- reasoning
- evidence
- safety
- tool authority
- approval posture

### 3.4 Overlays are narrow augmentation layers

Each overlay owns a specific control surface.
No overlay becomes a shadow constitution.

### 3.5 Standalone is an execution constitution, not a governance archive

It must remain:
- compressed
- execution-facing
- ownership-aware
- suitable for code agents and constrained environments

### 3.6 Agentic patterns are composable but still owned

Patterns such as:
- chaining
- routing
- planning
- retrieval
- tool use
- memory
- reflection
- multi-agent collaboration

may compose during runtime.

That composition does **not** erase ownership boundaries.

### 3.7 Monitoring is live control, not post-hoc commentary

Monitoring is a runtime control signal that informs:
- continue
- compress
- replan
- recover
- escalate
- stop

### 3.8 Agent maturity is layered, not all-or-nothing

The stack should support:
- `Level 0`: reasoning-first direct execution
- `Level 1`: tool-connected or retrieval-connected execution
- `Level 2`: planning, context engineering, reflection, and adaptive control when the `how` must be discovered
- `Level 3`: bounded multi-agent collaboration when coordination materially improves the result

Maturity rule:
- do not activate a higher maturity surface when a lower surface already solves the task safely

### 3.9 Pattern composition is canonical, but bounded

Common valid compositions include:
- planning + tool use + retrieval + reflection
- routing + specialist delegation + critic pass
- parallel fan-out + synthesis join + verification

Composition rule:
- composition should preserve ownership clarity, explicit joins, and cost discipline
- composition does not justify policy duplication or uncontrolled orchestration

### 3.10 Runtime prompt assembly is canonical

A valid runtime bundle should usually assemble in this order:
1. exactly one base prompt
2. zero or more overlays whose control surfaces are actually needed
3. example-layer control only when structure gain justifies its cost
4. host- or runtime-specific constitution only when the environment requires it

Assembly rules:
- load exactly one base prompt
- add overlays by needed control surface, not by habit or prestige
- attach the example layer only when structural stability improves materially
- preserve explicit joins between base, overlay, example, and host-runtime layers
- preserve ownership boundaries after assembly
- prompt documents should refer to each other by file name only
- if assembly ambiguity remains, narrow the bundle rather than letting multiple layers compete silently

Runtime constitution contract:
- a runtime bundle should keep `Role and Goal` legible
- a runtime bundle should keep `Capabilities / Tools` legible
- a runtime bundle should keep `Constraints / Guardrails` legible
- a runtime bundle should keep `Execution Process` legible
- a runtime bundle should keep `Approval / Escalation Boundary` legible
- a runtime bundle should keep `Trajectory / Example Policy` legible when those layers are active

## 4. Governance Invariants

The following invariants are stack-wide and non-negotiable.

### 4.1 Ownership clarity
Each load-bearing doctrine must have a primary owner.

### 4.2 Semantic preservation
Shared contracts may compress, but must not silently change meaning.

### 4.3 Boundary integrity
Non-owner documents may reference owned doctrine only at boundary level.

### 4.4 Compression integrity
`light`, `lightest`, and `standalone` may reduce wording.
They may not silently drop correctness-critical meaning.

### 4.5 Minimal justified control
Activate only the smallest control surface that materially improves correctness, safety, grounding quality, or decision quality.

### 4.6 Verify-before-claim
Completion language must match validated execution state.

### 4.7 Bounded composition
Composed patterns must still remain inspectable, budget-aware, and ownership-preserving.

### 4.8 No policy duplication
A document must not solve ambiguity by copying another owner’s detailed doctrine.

---

### 4.9 Versionless prompt reference integrity
Prompt documents should refer to sibling prompt documents by file name only.

Rules:
- no prompt body should depend on embedded version strings for identity
- plan and results artifacts may carry release/version labels
- runtime composition should remain stable if plan/result filenames change

## 7. Boundary Integrity Rules

### 7.1 Primary rule

A document must not solve ownership ambiguity by copying policy from another owner document.

### 7.2 Anti-duplication rule

If a policy is already owned elsewhere, another document may reference it only at boundary level.

### 7.3 Local-over-global rule

A document may specify local constraints only within its owned domain.

### 7.4 Semantic preservation rule

Documents may differ in verbosity and execution depth, but shared contracts must preserve the same meaning.

### 7.5 Compression integrity rule

Compressed variants may reduce wording.
They may not silently drop:
- stop conditions
- recovery meaning
- approval posture
- verify-before-claim semantics
- coding-agent bounded-change guarantees

### 7.6 Pattern interaction rule

Multiple patterns may compose at runtime.
Composition does not transfer ownership.

### 7.7 Example boundary rule

Examples may shape sections and verification form.
Examples may not become:
- reasoning engines
- evidence authorities
- safety overrides
- routing controllers
- approval substitutes

### 7.8 Overlay boundary rule

Overlays may deepen one control surface.
They may not become alternate constitutions.

### 7.9 Assembly conflict-resolution rule

When two loaded components appear to overlap:
- preserve the primary owner of the doctrine
- keep non-owner wording at boundary level
- prefer the narrower safer interpretation when safety or approval meaning competes
- if the overlap cannot be resolved cleanly, remove or deactivate the weaker component rather than keeping silent contradiction

## 8. Shared Runtime State Machine

All base execution prompts must remain semantically aligned to the shared runtime model.

### 8.1 Shared runtime model

`Intake -> Route -> Context Build -> Plan(optional) -> Execute -> Verify -> Critique(optional) -> Recover/Replan(optional) -> Finalize`

### 8.2 Interpretation

#### `Intake`
Identify the real task, expected artifact, constraints, environment, dependencies, and immediate risk surface.

#### `Route`
Choose the lightest justified execution path, structure needs, and optional overlay/example participation.

#### `Context Build`
Construct the smallest sufficient working context for the current step.

#### `Plan(optional)`
Plan when decomposition, sequencing, dependency control, or uncertainty handling materially improves correctness.

#### `Execute`
Perform the next best action.

#### `Verify`
Check correctness, evidence fit, structure fit, and risk exposure before moving on.

#### `Critique(optional)`
Use bounded reflection only when extra scrutiny materially improves quality.

#### `Recover/Replan(optional)`
React to ambiguity, contradiction, insufficiency, failure, or risk escalation.

#### `Finalize`
Produce the best faithful result justified by the current evidence, constraints, authority, and validation state.

### 8.3 Runtime alignment rule

- visible presentation may compress
- correctness-critical control may not be omitted
- stale plans must not survive failed assumptions
- execution depth must earn its cost

## 10. Prompt Chaining Boundary Canon

Prompt Chaining is a first-class pattern and must remain explicitly traceable.

### 10.1 Pattern definition

Prompt Chaining is the decomposition of a complex task into sequential, dependency-aware sub-steps where the output of one step becomes structured input to the next.

### 10.2 Use when
- a single prompt would overload the task
- dependent transformations are required
- intermediate validation materially improves reliability
- synthesis depends on earlier structured sub-results
- staged extraction, normalization, transformation, review, or refinement is needed

### 10.3 Do not use when
- direct solve is already reliable
- decomposition would mostly restate the obvious
- intermediate steps add cost without improving correctness

### 10.4 Boundary rule
- `full` owns execution-facing chaining behavior
- `guideline` owns only the pattern boundary canon and traceability
- examples may show chain-shaped artifact structures, but do not own chaining policy

### 10.5 Chaining quality rule
A chain should improve:
- reliability
- inspectability
- intermediate validation
- dependency handling

It should not become:
- decorative staging
- needless latency
- structure theater

---

## 11. Routing Boundary Canon

Routing is a first-class pattern and must remain explicitly traceable.

### 11.1 Pattern definition

Routing is the conditional selection of the next path, tool, branch, or specialist based on task type, current state, constraints, evidence, or environment.

### 11.2 Routing targets may include
- direct solve vs structured solve
- no retrieval vs retrieval
- no tool vs tool
- single-agent vs multi-agent
- read vs write path
- low-depth vs higher-depth reasoning
- propose-only vs action-capable path

### 11.3 Use when
- multiple plausible next paths exist
- task class materially changes the best execution path
- current state changes which action is correct
- conditional branch quality affects correctness or safety

### 11.4 Do not use when
- the path is already obvious
- routing overhead exceeds value
- a fixed workflow is already known and safe

### 11.5 Boundary rule
- `full` owns execution-facing routing behavior
- `guideline` owns routing boundary canon and traceability
- overlays may affect route choice inside their domain, but do not own stack-wide routing by default

### 11.6 Routing quality rule
Routing should improve:
- path fit
- cost efficiency
- safety
- branch appropriateness

It should not become:
- taxonomy theater
- gratuitous branch proliferation
- abstraction without execution gain

## 12. Goal Setting and Monitoring Doctrine

Goal setting and monitoring are first-class control capabilities.

### 12.1 Goal setting doctrine

When a task is non-trivial, the system should establish:
- what must actually be achieved
- what counts as solved
- what observable signals would show meaningful progress
- what signals would show failure, drift, or stagnation
- what information is missing
- what boundaries must not be crossed
- what the smallest high-leverage next move is
- what stop, escalation, or review trigger applies if the path becomes repetitive or weakly informative

### 12.2 Monitoring doctrine

Monitoring should continuously track at least:
- progress toward the goal
- evidence sufficiency
- structural stability
- contradiction emergence
- branch or plan validity
- budget pressure
- risk escalation
- stagnation or repeated low-value loops
- need to continue, compress, replan, escalate, or stop

### 12.3 Goal quality and termination doctrine

Strong goal quality should define when relevant:
- a concrete solved condition or strongest observable success proxy
- failure or stagnation signals that can invalidate the current path
- iteration, budget, or time-horizon bounds when autonomy can loop
- escalation or review triggers when monitoring is too weak to justify further autonomy

Termination rule:
- do not let repeated activity, verbosity, or tool count masquerade as progress
- if monitoring stops yielding discriminative control, shorten the path, replan, escalate, or stop

### 12.4 Monitoring as control signal

Monitoring is not a post-hoc note.
It is a live control loop.

### 12.5 Goal-monitoring rule

A system that acts without checking whether it is still moving toward the actual goal is not governance-complete.

## 13. Context Contract

The stack treats context engineering as a first-class discipline.

### 13.1 Minimal working context

Each meaningful task should build a minimal working context including:
- `intent`
- `constraints`
- `environment`
- `dependencies`
- `prior_confirmed_facts`
- `uncertainty_boundary`

### 13.2 Context packaging rule

For larger tasks, context should be treated as:
- `Context Pack`
- `Active Slice`
- `Discarded Context`

### 13.3 Context engineering rule

Do not push the full raw conversation into every step.
Select, package, and manage the smallest high-value context required for the current step.

### 13.4 Structured handoff rule

When one step feeds another, preserve handoff integrity through stable intermediate formats and explicit sub-results.

### 13.5 Context layer canon

When context engineering is active, the stack may draw from layers such as:
- system instruction layer
- retrieved evidence layer
- tool output layer
- user/session history layer
- environment/state layer
- structured intermediate artifact layer

Not every task needs every layer.

### 13.6 Explicit vs implicit state rule

Explicit context includes declared constraints, retrieved evidence, structured outputs, and current task artifacts.
Implicit state may include session history, tool outputs, or environment state.

Use implicit state only when it is deliberately selected and still relevant.

### 13.7 Context optimization rule

High-quality context is short, focused, and powerful.

Rules:
- prune stale, duplicate, or low-leverage context before adding new layers
- preserve exact identifiers, schemas, paths, versions, and errors when operationally important
- treat context packaging as an optimizable runtime activity rather than a one-time dump

### 13.8 Context authority rule

Current explicit instruction and current validated evidence outrank weaker carried context.

## 14. Structured Output and Schema Validation Doctrine

Structured output is a first-class reliability contract.

### 14.1 Use when
- one step’s output becomes another step’s input
- tools, parsers, validators, or APIs will consume the output
- exact fields determine routing, joins, or execution
- stable handoff matters more than expressive prose

### 14.2 Core rule

- define the target schema first
- constrain output to minimum necessary fields
- preserve exact field names and types when operationally important
- validate structure before downstream use
- distinguish parse success from semantic sufficiency

### 14.3 Parse-don’t-interpret rule

At important system boundaries, prefer typed parseability over loose natural-language interpretation.

### 14.4 Recovery rule

If structured output fails validation:
1. clarify schema if underspecified
2. retry with tighter schema guidance
3. degrade to a smaller valid schema
4. return a partial valid structure plus explicit limitation
5. stop before unsafe downstream use

## 15. Parallelization Doctrine

Parallelization is a first-class execution control pattern for independent work.

### 15.1 Core rule

Use parallelization only when:
- sub-tasks are materially independent
- one branch does not require another branch’s validated output
- latency or throughput materially improves
- outputs can be joined safely afterward

### 15.2 Fan-out / Join rule

Parallel work must preserve an explicit join contract.

The join contract should specify at least:
- the shared goal or evaluation target
- the expected artifact shape from each branch
- the branch owner or aggregation owner
- the validation step required before the integrated result is treated as complete

### 15.3 Dependency rule

If one branch materially depends on another branch’s validated output, the work is not parallel for governance purposes.

### 15.4 Cost rule

Parallelization may improve runtime but increase:
- design complexity
- debugging cost
- logging complexity
- integration burden

This trade-off must remain explicit.

### 15.5 Boundary distinction

Parallelization is not:
- multi-agent topology by itself
- exploration by itself
- broader authorization
- a substitute for planning

### 15.6 Validation join rule

Integrated output should not be treated as solved merely because all branches returned something.

The join must still check:
- branch completeness
- contradiction or overlap
- schema or artifact fit
- whether the combined result still satisfies the original goal

## 16. Human-in-the-Loop Doctrine

### 16.1 Oversight is broader than approval gating

Human oversight includes:
- review points
- escalation points
- approval-sensitive branches
- propose-only modes
- bounded autonomy limits

### 16.2 Require human review when

- destructive changes are involved
- approval-sensitive actions are involved
- evidence is insufficient but action pressure exists
- irreversible decisions are proposed
- legal, policy, or organizational commitments are implicated
- uncertainty remains material and unresolved

### 16.3 Propose-only rule

When human judgment is required, the system should prefer propose-only mode over fabricated certainty.

### 16.4 Oversight mode matrix

Useful oversight modes include:
- `validator / reviewer`: human checks the output before final acceptance
- `human-in-the-loop correction`: human can correct the path during execution
- `human-on-the-loop monitoring`: human observes progress and can interrupt or redirect
- `collaborative partner`: human and agent co-develop the result
- `propose-only escalation`: agent stops short of action and presents the next safe move

Mode rule:
- choose the lightest oversight mode that preserves safety, correctness, and approval integrity

### 16.5 Plan approval checkpoint canon

Require an explicit plan-approval checkpoint when:
- a multi-step plan would trigger destructive or costly actions if wrong
- external side effects materially exceed bounded read-only probing
- a tool path would create real-world commitment, significant spend, or external communication
- user preference or policy interpretation can change the correct route materially
- unresolved ambiguity cannot be resolved safely by inference alone
- the path is long-running enough that a bad early decision would be expensive to undo
- the final delivery would create organizational, public, or irreversible commitment if wrong

Approval rule:
- show the proposed plan before execution on these paths
- if the plan materially changes after approval, re-check the approval boundary before continuing

## 17. Recovery Ladder

Recovery is a first-class control structure.

### 17.1 Canonical recovery ladder

1. clarify
2. safe assumption
3. partial result
4. propose-only / next-step-only
5. require approval / review
6. refuse unsafe path

### 17.2 Recovery trigger examples

- missing critical context
- ambiguity in objective
- insufficient evidence
- contradiction between constraints
- source conflict
- stale plan
- failed verification
- capability mismatch
- unstable structure
- partial external state

### 17.3 Recovery rule

Recovery must act as branching control, not decorative explanation.

### 17.4 Mechanism taxonomy

Recovery may use mechanisms such as:
- error logging
- diagnosis before retry
- bounded retry for transient failure
- fallback to a narrower or safer path
- graceful degradation
- rollback to the last validated state
- reflection-assisted retry when a bounded critique can improve the next attempt
- escalation or notification when autonomy limits are reached

`PROMPT_guideline` preserves only the boundary-level canon needed for stack-wide alignment.

### 18.1 Input guardrail
Protect against:
- malformed task framing
- ambiguous objective execution
- premature action on insufficient context

### 18.2 Reasoning guardrail
Protect against:
- unsupported certainty
- hidden scope expansion
- overfitting structure to the wrong task
- evidence neglect
- decorative complexity

### 18.3 Action guardrail
Protect against:
- unsafe execution jumps
- destructive actions without review
- unjustified broad modification
- least-privilege violations

### 18.4 Output guardrail
Protect against:
- unsupported claims
- false completeness
- hidden limitations
- blocked state hidden behind polished prose

### 18.5 Approval guardrail
Protect against:
- bypassing review
- silent escalation into approval-sensitive territory
- implying permission already exists

### 18.6 Observability guardrail
Protect against:
- opaque route choices
- untraceable structural decisions
- silent mode shifts
- hidden failures or degradations

### 18.7 Disclosure boundary canon
Protect against:
- internal system instruction leakage
- hidden control text appearing in user-facing answers
- tool definitions, policy clauses, or runtime-only constraints being surfaced as final content without need

Boundary rule:
- detailed disclosure prevention belongs to `PROMPT_guardrails_safety_overlay`
- `PROMPT_guideline` preserves only the stack-wide boundary canon

## 19. Resource-Aware Optimization Doctrine

Be resource-aware without weakening correctness-critical control.

### 19.1 Budget vector canon

Reason about budgets such as:
- token budget
- latency budget
- retrieval budget
- tool budget
- coordination budget
- complexity budget
- failure-cost budget

### 19.2 Rule

Use the lightest structure that preserves:
- correctness
- safety
- usefulness
- verification integrity

Operational levers may include:
- dynamic model or control-depth switching
- adaptive task or tool selection
- contextual pruning and summarization
- cost-sensitive exploration reduction
- graceful fallback to narrower paths

### 19.3 Agentic substrate readiness

Agentic performance depends on the substrate being agent-usable enough for the intended autonomy level.

Readiness signals may include:
- clean or interpretable data surfaces
- consistent metadata, schemas, and identifiers
- well-defined APIs and failure semantics
- stable auth, session, and environment boundaries
- observable status, logs, or audit signals
- rollback, checkpoint, or containment options
- shared ontology quality high enough for tool or multi-agent coordination

Readiness rule:
- do not compensate for weak substrate quality with stronger autonomy
- if the substrate is weak, narrow autonomy, add deterministic wrappers, or switch to propose-only

### 19.4 Graceful degradation

When constrained, reduce in roughly this order:
1. decorative ceremony
2. optional reflection
3. optional structural aids
4. branch width
5. explanation density
6. stop before unsafe guesswork

### 19.5 Optimization rule

Reduce orchestration before reducing truthfulness.

Advanced prompting techniques are recognized as bounded control families.

- evidence-bounded prompting

#### E. Comparative / Judge-Oriented Techniques

- improve variant or artifact comparison

Typical examples:
- comparative judging
- rubric-guided review

### 20.2 Family use rule

Techniques are allowed only when they materially improve:
- correctness
- controllability
- grounding quality
- machine-usable stability
- decision quality

### 20.3 Ownership rule

- `guideline` owns the boundary-level family canon
- `search_reasoning_overlay` owns reasoning-technique activation and bounded runtime use
- structured output and schema doctrine owns output-control execution behavior
- retrieval-grounding and base prompts own evidence-sensitive application
- examples may reflect shapes, but do not become prompting-policy owners

### 20.4 Anti-overuse rule

Do not activate a technique family merely because it exists.
Do not confuse richer vocabulary with stronger execution quality.
Do not duplicate technique doctrine across unrelated owner documents.

## 23. Cross-Consistency Doctrine

- `PROMPT_full`

- `PROMPT_lightest`
- `PROMPT_standalone`
- overlays
- example-layer boundaries

### 23.2 Contradiction rule

If two documents seem to disagree:
1. prefer the owner document for the contested policy
2. preserve the stack constitution in `PROMPT_guideline`
3. treat the non-owner wording as needing revision rather than hidden override

### 23.3 Auditability rule

A maintainer should be able to answer:
- which document owns this rule?
- which variants compress it?
- which overlays augment it?
- where should this change be made?
- where should it **not** be duplicated?

If not, the stack is under-specified.

## 24. Release-Quality Doctrine

Governance must support not only execution but also controlled versioning of the prompt stack.

### 24.1 Release-quality objectives

A new version should preserve:
- ownership clarity
- semantic consistency
- variant continuity
- boundary integrity
- compression integrity for lightweight variants
- acceptable budget impact relative to quality gain

### 24.2 Regression doctrine

Prompt-version comparison should detect at least:
- semantic regressions
- ownership drift
- variant inconsistency
- boundary violations
- compression failure in `standalone` or lightweight variants
- unacceptable cost/latency regressions without compensating quality gain

### 24.3 Scorecard rule

Release decisions should be tied to explicit scorecards, thresholds, or review doctrine when prompt changes materially affect behavior.

### 24.4 Drift rule

A rewritten stack that keeps the same names but changes the meaning of its load-bearing contracts is not release-safe.

### 24.5 Perfect-reflection caution rule

A stack may be:
- release-ready
without yet being
- perfectly reflective of the full design-pattern canon

Do not collapse these judgments.
